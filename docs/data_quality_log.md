# Data Quality Log

Every issue found in the raw data and the decision taken, in order.

| # | Column | Issue found | Decision | Reason |
|---|--------|-------------|----------|--------|
| 1 | Ticket Description | 6,150 descriptions contain line breaks inside quoted fields; opening the CSV directly in Excel can split rows | Load the file only through Power Query (UTF-8, comma delimiter) | Keeps the row count at 8,469 and the text intact |
| 2 | All typed columns | Windows regional settings can misread `3.0` or `2021-03-22` | Set data types with *Change Type → Using Locale → English (United States)* | Values are stored in US format; checked CSAT = 1–5, purchase dates 2020-01-01 to 2021-12-30, age 18–70 |
| 3 | Resolution | 5,700 blanks were imported as empty strings (`""`), not nulls, so they were counted as filled | *Replace Values* `""` → `null` in Power Query | Text columns import blanks as empty text; date and number columns convert blanks to null automatically. Without this, null counts are wrong |
| 4 | Resolution, Time to Resolution, Customer Satisfaction Rating, First Response Time | ~5,700 blank values. Profiling by `Ticket Status`: Closed (2,769) has every field filled; Pending Customer Response (2,881) has no resolution, resolution time or rating; Open (2,819) also has no first response | Keep as nulls — no deletion, no imputation | Blanks belong to tickets that are not finished yet, so they are expected, not errors. Deleting would remove two-thirds of the tickets; filling would invent resolutions and ratings that never happened |
| 5 | Whole dataset | Signs of synthetic data: categories split ~25% each (gender, channel, priority, type); all 8,469 descriptions contain the template text `{product_purchased}`; 139 emails appear on more than one ticket | Treat findings with caution; validate differences before presenting them (Stage 3) | Synthetic data tends to show weak patterns; stating this openly avoids presenting random noise as insight |
| 6 | Customer Name, Customer Email, Ticket Description, Resolution | Personal data (name, email); description is template text containing `{product_purchased}`; resolution is filler text | Removed from the clean dataset | Personal data must not be published; the other two carry no analytical information (ticket status already shows whether a ticket was resolved) |
| 7 | All columns | Column names contain spaces and mixed case; text values may have stray spaces or hidden characters | Renamed to snake_case; applied Trim and Clean to all text columns | snake_case avoids brackets in SQL (Stage 2) and is the industry convention |
| 8 | customer_age, priority | Age is too granular for comparison; priority sorts alphabetically (Critical, High, Low, Medium) | Added `age_group` (18-24, 25-34, 35-44, 45-54, 55-64, 65+) and `priority_order` (Low=1 … Critical=4) | Age bands make segments comparable; the numeric order lets Power BI sort priority correctly |
| 9 | ticket_subject | 16 subjects are too many to answer "is it a product defect or a service problem?" | Added `issue_category` (Product defect 3,171 · Usage & setup 2,639 · Service & billing 2,659) via a mapping file `data/reference/subject_mapping.csv` merged in Power Query (left outer join, unmatched → `Unmapped`, 0 found) | The core business question is whether problems come from the product or from the service; a separate mapping file keeps the rule visible and easy to change |
| 10 | ticket_type vs ticket_subject | The two columns often contradict each other (e.g. 100 tickets typed "Billing inquiry" with subject "Hardware issue") | `issue_category` is built from `ticket_subject`, not `ticket_type` | The subject describes the actual problem more specifically; the contradiction is another sign of synthetic data |
| 11 | first_response_at, resolved_at | Both are timestamps, not durations, and all 8,469 fall between 2023-05-31 and 2023-06-02 while purchases span 2020–2021. In 1,365 of 2,769 closed tickets the resolution happens *before* the first response. There is no ticket-created timestamp, so time to first response cannot be calculated | Keep the raw timestamps, create **no** duration column, and exclude response/resolution speed from the analysis | The evidence points to generated data, not customer behaviour (impossible tickets still have satisfaction ratings). Any duration built on it would look valid but be wrong. "I chose not to answer a question my data couldn't support" |
